Research

My work centers on enhancing the reliability and efficiency of programs with large language models (LLMs). Neither property can be judged from a program's final output alone, so every project pairs an LLM that interprets the natural-language specification with deterministic rules, constraint solvers, and actual execution that verify the result. The projects below form two lanes that each move from predicting or measuring a property to exposing or enforcing it.

Efficiency: from predicting cost to exposing bottlenecks

Efficiency asks how much computation a program needs and where its bottlenecks arise. I started by predicting the answer and moved toward generating the inputs that make it observable.

  1. TCProF NAACL 2025 Predicts time complexity with few labeled examples, using code augmentation and a symbolic module inside a co-training loop.
  2. MEC³O arXiv 2025 Replaces a single predictor with per-class expert LLMs that debate and reach a weighted consensus, improving prediction without new labels.
  3. STAB arXiv 2026 Goes beyond prediction: from the specification alone it generates inputs that trigger the worst-case path, so inefficiency is verified by running the program rather than estimated.

Reliability: from measuring contract compliance to enforcing it

Reliability asks whether generated code satisfies not only the required functionality but also the input contracts written into the specification. I first built a way to measure this, then a way to improve it, and most recently a way to establish where generated code came from, since code that cannot be traced to its source cannot be trusted either.

  1. ContractEval Findings of ACL 2026 A benchmark that checks whether generated code rejects contract-violating inputs, built with an LLM–SMT pipeline that synthesizes one violating input per contract and keeps only tests confirmed by execution.
  2. SLICE arXiv 2026 A generation method that isolates contract enforcement from functional implementation at the specification level, selecting candidates by execution and screening assertions before merging them.
  3. SEW arXiv 2026 A provenance method that watermarks already generated code by choosing among equivalent code styles with a secret key, leaving functionality untouched, and detects the watermark with evidence calibrated against human style preferences and aggregated by structural context.

How the lanes connect

STAB and SLICE both start from the same object, the natural-language specification, and both let execution be the judge: STAB runs the program on generated inputs, SLICE runs candidate bodies and assertions on specification examples. ContractEval supplies the evaluation setting that SLICE improves on. SEW extends the reliability lane from what the code does to where it came from, and it keeps the same habit: explicit style rules do the embedding, and calibrated evidence does the verification. Across all six projects the division of labor is the same: the LLM handles interpretation, and structuring plus verification are delegated to rules, solvers, and execution.

Applied track: Korean dialect NLP

Alongside the main line, I work on Korean dialect toxicity and translation. These projects share the same habit of pairing LLMs with explicit structure: curriculum schedules, spectral features, and dictionary-based pre-processing.
